# 启动与课程通知修复（2026-11-02）

## 原因与修复

原生版把初始页面判断绑定到 `loading`。缓存加载后立即启动联网刷新，会在页面判断执行前重新进入 loading，导致首页等待网络。现在以独立的 `initialized` 标记决定首屏，缓存与账号解密并行、偏好文件延迟到 IO 线程读取，联网刷新在内容首帧后启动；隐藏标签页预热也推迟到首屏之后。账号恢复不会覆盖期间发生的新登录或退出。

迁移后的启动流程没有重新发布本地课程时间表，也遗漏了恢复前台及权限变化后的重排。通知因而依赖联网刷新成功，旧时间表过期、离线或新授予权限时可能保持静默。现在启动、恢复前台、权限回调、重启、升级和日期/时间/时区变化都会用缓存恢复调度，不需要网络登录。缓存写入与通知发布共用进程内锁，恢复回调不会用旧 UI 快照覆盖新课表。时间表覆盖剩余学期，取消原有约 60 天窗口。

## 课前提醒

- 每个实际小节提前 10 分钟，第 1、5 节提前 20 分钟。
- 使用普通/错峰教学楼的实际时间与手动作息修正。例如第 1 节普通楼 08:00 上课、07:40 提醒，错峰楼 08:10 上课、07:50 提醒。
- 独立开关及 `course_preclass_reminders` 渠道，默认开启，不受实时活动关闭或“今天不再显示”影响。
- 只安排最近一个提醒，触发后接续；持久化防重复，同一时刻的课程合并显示。过期课程、已删除课程及旧闹钟不会补发。首次新建调度不追补错过的触发点；已经排定的闹钟延迟到课前到达时仍可提醒，上课后不补发。
- 与课间状态变化同一时刻触发时，先核对已经排定的提醒，再替换下一闹钟，避免两个接收器互相取消。

通知、实时活动、提醒渠道和“闹钟和提醒”状态在权限页分别显示，设置保存后立即重排。拒绝过且无法再次弹窗时打开系统设置。精确提醒需要系统允许准时闹钟；未允许时使用非精确闹钟兜底，可能延迟。厂商后台与自启动限制仍由系统管理。

## 验证

- 优化预览版及独立 benchmark 构建通过，98 项应用 JVM 测试通过，零失败/跳过。新增用例覆盖 10/20 分钟、错峰、后续小节、重复、迟到/失效闹钟、同刻课程、旧缓存及完整学期时间表。
- OnePlus / Android API 37，保持解锁和固定竖屏，三次冷进程启动的 Android `Fully drawn` 为 262、264、267ms，首帧为 116、121、130ms。这是该设备当前本地配置的有限观测，不是所有设备、账号或大课表的性能保证。旧版未上报 fully drawn，不能用它计算同口径改善百分比；锁屏期间的测量已排除。
- 独立 benchmark UID 的框架 Instrumentation 实测通过：上课纯数字倒计时、课间时间地点与课程时长、系统提升显示、实时活动关闭时独立提醒、真实 AlarmManager 投递、防重复、完成状态可清除、无课日不通知及清理。
- 合成课程安排在约 10 分钟 4 秒后，以真实时钟验证提前 10 分钟的闹钟；约 4 秒后到期，观测投递延迟约 1025ms。没有修改手机时钟或使用真实账号数据。测试前台宿主仅属于 benchmark，不进入预览/正式 APK；厂商限制下的长期后台、省电和重启投递未作全场景实测。

真机原始结果、日志和截图位于被忽略的 `native/artifacts/`。预览版覆盖安装保留应用数据；临时 benchmark 应用及合成通知在测试结束后移除。

参考：[Android 启动指标](https://developer.android.com/topic/performance/issues/launch-time)、[实时活动](https://developer.android.com/develop/ui/views/notifications/live-update)、[闹钟与精确权限](https://developer.android.com/develop/background-work/services/alarms)。
